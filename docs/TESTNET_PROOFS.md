# Testnet proofs: Airlock reputation anchored on Stellar

Generated by `scripts/testnet_attest.py`. Machine readable copy: [testnet/proofs.json](testnet/proofs.json).

- Network: **Stellar TESTNET** (`stellar:testnet`), Horizon `https://horizon-testnet.stellar.org`. No mainnet, no real funds.
- Run started 2026-10-22T18:51:13Z, finished 2026-10-22T18:51:40Z (UTC).

## What was tested

1. Three testnet wallets: an Airlock operator and two MCP servers (an honest weather server and a calc server that ships a poisoned tool).
2. A `ReputationAirlock` with `HARNESS_POLICY` inspected the demo request `demo/requests/02_mcp_poisoning.json` (tool order varied per round) and clean requests with `mcp__weather__get_forecast` until the calc server was blocked.
3. Each server subject was bound to a local agent id, turned into an attestation document (ERC-8004 feedback shape) and its sha256 was anchored in one testnet transaction: a 0.0000001 XLM payment operator -> agent wallet with `Memo hash` = document hash, plus a `ManageData` entry `airlock:rep:<agent[:8]>` on the operator account holding the same 32 bytes.
4. Both transactions were re-read from Horizon and checked against the documents.
5. A tampered copy was rejected; a fresh Airlock inherited reputation from the ledger.

## Limitations

- Testnet only. Testnet is reset periodically, so these links can disappear after a reset; `proofs.json` and the attestation files keep the hashes.
- The ERC-8004 feedback SHAPE is anchored on Stellar; nothing is written to the official ERC-8004 EVM registries.
- Agent ids (1 = calc, 2 = weather) are local stand-ins for ERC-8004 agentIds. On Stellar the agent identity is the agent wallet address.
- The chain proves who attested what and when, not that the score is fair: an importer still decides which operators to trust.
- Operator key custody is out of Airlock's scope: the script reads keys from a file outside the repo (chmod 600); Airlock itself never stores keys.
